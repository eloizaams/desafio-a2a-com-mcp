# Desafios e fricções recorrentes

Ler no início de cada sessão. Formato: problema → como lidar.

- **Validador exige processos recém-iniciados.** Reservas criadas numa execução mudam a seguinte → sempre usar a skill `rodar-validador` (reinicia tudo).
- **git-flow CLI não instalado.** Git flow é manual (ADR-0007) → usar skill `git-flow` (`.claude/skills/git-flow`); nunca commitar em `main`/`develop`.
- **`uv` no terminal do VS Code (snap) cai no diretório errado.** O snap redefine `XDG_DATA_HOME`, e o instalador põe o binário em `~/snap/code/<rev>/.local/bin` (some quando o VS Code atualiza). Instalar com `curl -LsSf https://astral.sh/uv/install.sh | env UV_INSTALL_DIR=$HOME/.local/bin UV_NO_MODIFY_PATH=1 sh`. Já instalado: uv 0.12.23 em `~/.local/bin`.
- **Agente de commit:** o CLAUDE.md global cita "caverman-commit"; o que existe é a skill `caveman-commit`.
- **Pasted text longo pode não chegar.** O enunciado completo está no `README.md` do starter (será substituído na entrega → cópia em `docs/specs/ENUNCIADO.md`).
- **MCP rejeita `Host: testserver` com 421** (proteção DNS rebinding do SDK). Em testes ASGI usar `TestClient(app, base_url="http://127.0.0.1:7301")`.
- **`pkill -f <padrão>` mata o próprio shell** quando o padrão aparece na linha de comando do Bash. Derrubar processos por porta (`fuser -k 7301/tcp`) ou por PID (`$!`).
- **Cliente MCP do SDK só anuncia `elicitation` se houver `elicitation_callback`.** Passar um callback-guarda que levanta erro e sempre chamar `client.session.call_tool(..., allow_input_required=True)` — nunca `Client.call_tool` (fecha o MRTR sozinho). Ver ADR-0003.
- **ruff N818 desligado:** exceções seguem o domínio em português (`ErroX`).
- **MRTR do SDK só funciona via `Annotated[..., Resolve(fn)]`.** Devolver `Elicit` do corpo da tool não gera `input_required`; e `Elicit` exige classe pydantic (enum dinâmico via `create_model` + `Literal`). Resolver só lê; a tool grava. Detalhes na ADR-0006 (notas da fase 002).
- **`Annotated[T, Resolve(fn)]` não pode referenciar `fn` por variável local do closure** quando o módulo tem `from __future__ import annotations` (todos os adapters têm). A anotação vira string, e o SDK monta o `inputSchema` com `inspect.signature(fn, eval_str=True)`, que só resolve nomes em `fn.__globals__` — não vê o escopo da função externa (ex.: `criar_app`) → `InvalidSignature: Unable to evaluate type annotations`. Contorno: definir a tool sem anotar o parâmetro problemático, atribuir os tipos reais direto em `tool_fn.__annotations__` (objetos, não strings) e registrar com `servidor.tool(...)(tool_fn)` em vez do `@decorator` (que roda antes do patch). Ver `adapters/mcp/server.py` (`reservar_sala`).
- **`mypy --strict` só casa uma função solta com um `Protocol` de `__call__` assíncrono se os nomes dos parâmetros baterem exatamente** com os do protocolo (ex. `ElicitationFnT.__call__(self, context, params)`), não só os tipos — `(ctx, req)` ou `(_contexto, _pedido)` falha com "incompatible type", mesmo com tipos idênticos. Reproduzido isolado (ver `agente/src/agente_salas/adapters/mcp_client/cliente.py`, `_recusar_elicitation`): renomear os parâmetros para o nome do protocolo resolve.
- **`mcp_types.RequestParamsMeta` é um `TypedDict` aberto (`extra_items=Any`, PEP 728)**, mas o mypy 2.4 ainda não infere chaves extras (ex. `traceparent`) num dict literal passado direto pro parâmetro `meta=` — erro "Extra key" ou falha de overload. Contorno: montar com `cast(types.RequestParamsMeta, {...})` num helper só pra isso (`_meta()` em `cliente.py`).
- **`mcp.Client` aceita um `MCPServer`/`Server` direto como "servidor"** (em vez de URL), despachando em processo sem rede nem framing JSON-RPC — útil pra TDD de cliente sem subir HTTP de verdade. Ver `agente/tests/unit/adapters/mcp_client/fake_servidor.py` (espelha `reservar_sala`/`politica://uso` do servidor real, sem import cruzado).
- **`a2a-sdk==1.2.2` exige o header `A2A-Version: 1.0` em todo `SendMessage`/`GetTask`, senão recusa com `-32009`** (trata ausência como v0.3; `enable_v0_3_compat` só reconhece os nomes de método da v0.3, como `message/send`, não os da v1.0 usados aqui). Nem `exemplos/wire/08-a2a-send-message.json` nem `validador/validar.py` mandam esse header — não é exigido pelo enunciado. Contorno: `ContextoComVersaoPadrao` (`agente/src/agente_salas/adapters/a2a/contexto.py`), um `ServerCallContextBuilder` que assume `1.0` quando o header vier ausente, passado para `create_jsonrpc_routes(..., context_builder=...)`.
- **`a2a-sdk==1.2.2` não tem `GetTaskResponse`** (só `SendMessageResponse`, que embrulha com `{"task": {...}}`). O `GetTask` devolve o `Task` cru direto em `result`, sem o wrapper `"task"` que aparece em `exemplos/wire/09-a2a-get-task-input-required.json`. Não há como corrigir sem reescrever o dispatcher JSON-RPC do SDK — o próprio `validador/validar.py` já contempla isso (`tarefa_de()` faz `resultado.get("task") or resultado`), então não afeta os checks V21–V36.
- **AgentExecutor do a2a-sdk exige que o 1º evento de cada `execute()` seja um `Task` completo**, não um `TaskStatusUpdateEvent` (`TaskUpdater.submit()`/`.start_work()` sozinhos levantam `InvalidAgentResponseError: Agent should enqueue Task before TaskStatusUpdateEvent event`). Usar `a2a.helpers.new_task_from_user_message(context.message)` e `event_queue.enqueue_event(...)` antes de qualquer `updater.*`. Ver `agente/src/agente_salas/adapters/a2a/executor.py`.
- **`a2a-sdk==1.2.2`: `SendMessage` só com `taskId` (sem `contextId`) ganha um `contextId` aleatório** — o handler V2 monta o `RequestContext` com `task=None`. Quebra o `history` e o `TaskManager` (`Context in event doesn't match`). Contorno: `ContextoDaTaskExistente` em `agente/src/agente_salas/adapters/a2a/contexto.py`. Detalhes na ADR-0002 (notas da fase 005).
- **Nunca abrir um `mcp.Client` por Task/requisição no agente:** o id JSON-RPC recomeça em 1 a cada instância → retry MRTR com id repetido. Um `ClienteSalas` por processo (lifespan do app). E o SDK só faz `tools/list` depois do 1º `tools/call` — a descoberta explícita (lazy) é nossa. Ver ADR-0003.
- **Teste que passa no `TestClient` pode falhar no validador:** o validador manda `traceparent` e omite `contextId` em continuações, e roda contra uvicorn. Conferir sempre com `rodar-validador` + `logs/agente.log` (Traceback), não só com o pytest.
- **`a2a-sdk==1.2.2` solta um Traceback intermitente e inofensivo no stderr do agente** (`Failed to detach context`, `GeneratorExit`, `ValueError: ... was created in a different Context`, `Task was destroyed but it is pending!`), vindo de `opentelemetry/.../a2a/utils/telemetry.py` no `EventQueueSource._dispatch_loop` de uma Task. Reproduzido num clone limpo (fase 6, T6.4): apareceu 4x no meio de uma execução 36/36 do validador; outra execução idêntica, minutos antes, deu 0. Não é causado pelo nosso código (nenhuma tool/executor nosso aparece na stack) e nunca correlacionou com um FAIL. `grep -c Traceback` sozinho não basta — grep por `Failed to detach context` para distinguir esse ruído de um traceback nosso de verdade.
- **`taskId` de continuação vai dentro de `message`, não em `params`** no `SendMessage` (`params.message.taskId`, não `params.taskId` — ver `exemplos/wire/10`). Mandar em `params.taskId` não dá erro: o `a2a-sdk` silenciosamente abre uma Task nova.
